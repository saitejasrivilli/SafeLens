# Evaluation — Phase 3 Baseline & Phase 4 DeBERTa

All numbers below come from `benchmarks/results/baseline/experiment.json`, generated by
`scripts/train_baseline.py` (`make baseline-train`). Measured locally on Apple M2. Not
production-scale, not comparable to full-corpus results.

## Metrics computed

Accuracy, precision, recall, F1, macro F1, PR-AUC, ROC-AUC, false-positive rate,
false-negative rate, confusion matrix, positive-prediction rate. **Accuracy is not the
headline metric** — at a 5% positive rate, a model that predicts "not toxic" for everything
scores ~95% accuracy while being useless for moderation. Precision/recall/PR-AUC and the
false-negative rate (missed toxic content) are the metrics that matter here.

## Threshold selection

**Criterion:** maximize F1 on the validation set (config: `decision_threshold.selection_metric: f1`).
**Selected threshold: 0.5** — validation F1 0.362, the maximum across all 9 candidates.
Selected and frozen using validation data only; the test set was not touched until after
this selection (`scripts/train_baseline.py`, test set evaluated exactly once, after the
threshold is fixed).

Note the sweep shows the standard precision/recall tradeoff: low thresholds catch nearly
all toxic comments (recall 1.0 at 0.1) at the cost of an unusable 97% false-positive rate;
high thresholds are precise but miss almost everything (recall 0.016 at 0.9). 0.5 is the
best F1 balance point for this baseline, not necessarily the right operating point for a
real moderation policy — that tradeoff (cost of a missed violation vs. cost of a false
block) is a Phase 10 policy-engine decision, not a Phase 3 modeling decision.

## Training time / inference performance (measured locally on Apple M2)

- Training time (TF-IDF fit + transform + Logistic Regression fit): **0.65s** on 5,588
  training examples.
- Inference: `model.predict_proba` on the already-vectorized test set (1,197 examples) —
  **~5.98M examples/sec, ~0.00017ms/example**. This measures only the Logistic Regression
  forward pass, not TF-IDF vectorization time, and reflects the trivial cost of a linear
  model on a small test set — not a representative production throughput number.

## Reproducibility

The full pipeline was run twice end-to-end (same dataset manifest, same config, same
seed=42). All threshold-sweep values, selected threshold, validation metrics, test metrics,
and artifact hashes were bit-identical between runs; only wall-clock timing fields differed.

## Limitations

- PR-AUC 0.27 / test F1 0.28 reflect a genuinely hard problem at this data scale (61
  positive examples in the test set) and a bag-of-n-grams model — not a bug. This is the
  number Phase 4 (DeBERTa) should be compared against honestly, not something to improve by
  changing Phase 3's methodology after the fact.
- Metrics are only for `toxicity`; the other 6 dataset dimensions are unevaluated (Phase 3
  scope, see `docs/model_design.md`).

# Phase 4 — DeBERTa-v3-small

All numbers below come from `benchmarks/results/deberta/experiment.json`, generated by
`scripts/train_deberta.py` (`make deberta-train`), run on **Google Colab GPU** (Linux,
CUDA T4, `torch==2.11.0+cu128`) — local M2 training was measured infeasible (§12,
`docs/model_design.md`) and this is explicitly labeled, not conflated with the M2 baseline
numbers above. Same dataset, same split, same `toxicity` target, same `ground_truth_threshold=0.5`
as Phase 3 — see `docs/model_design.md` §11-18 for full methodology.

## Training

3 epochs, 602.9 seconds (~10 min) on a Colab T4. Model selection used validation PR-AUC
(`load_best_model_at_end=True`); epoch 3 (validation PR-AUC 0.677) was selected as the final
model over epoch 1 (0.372) and epoch 2 (0.670).

## Error analysis

From `error_analysis` in `experiment.json` (threshold=0.9): 25 false positives, 33 false
negatives on the test set (n=1197). civil_comments is CC0-licensed; excerpts below are
truncated to ~100 characters, not reproduced in full.

**High-confidence false positives** (model very confident, wrong) — the two clearest
patterns:
- Sarcasm/hyperbole about a low-stakes topic read as toxic: *"Anyone who thinks Star Trek is
  superior is obviously a complete nincompoop..."* (prob 0.992, true label: not toxic). The
  model appears to key on the insult word ("nincompoop") without registering that the
  target/context (a fandom debate) makes it playful, not toxic.
- General frustration/cynicism about groups ("kids today", "buffoons... supporting them")
  scored highly toxic despite falling under the annotators' non-toxic majority — likely
  because the vocabulary overlaps heavily with genuinely toxic complaints-about-groups
  language, and the model has no way to distinguish generic cynicism from targeted hate at
  this size/training budget.

**High-confidence false negatives** (model very confident, wrong) — the clearest pattern:
- Toxicity expressed through metaphor or indirect language rather than direct insults/slurs,
  e.g. a corruption accusation phrased as *"a big, fat, juicy pig, gorging itself at the
  taxpayer's trough"* (prob 0.004, true label: toxic) and a comment dismissing a religious
  community's view on same-sex relationships in measured, non-slur language (prob 0.010,
  true label: toxic). Both are toxic by the dataset's human-annotator judgment but contain
  none of the surface-level toxic vocabulary a model (or TF-IDF) would key on — this is
  exactly the class of error contextual models are expected to still struggle with without
  more targeted training data or larger scale.

No clear evidence of truncation-related errors was found (texts are short comments, well
under the 256-token max sequence length in nearly all cases) — the errors above are content
understanding failures, not preprocessing artifacts.

## Inference benchmark

Measured on Google Colab GPU (T4, `cuda:0`), batch size 1, sequence length 256, 5 warmup +
50 measured iterations, distinguishing model-only vs. end-to-end (tokenization + forward
pass):

| | model-only | end-to-end |
|---|---|---|
| P50 | 15.56ms | 15.64ms |
| P95 | 17.79ms | 17.75ms |
| P99 | 18.83ms | 21.54ms |
| throughput (single-request) | 64.4 examples/sec | 63.2 examples/sec |

Batched throughput (batch size 32, full 1,197-example test set): **86.1 examples/sec**.

**This is a GPU number, not an M2 number** — it is not directly comparable to the baseline's
M2 CPU inference numbers (`~5.98M examples/sec` for the linear model) for a serving-cost
decision. A fair serving comparison would require benchmarking both models on the same
target deployment hardware (e.g. both on CPU, or both on the same GPU).

## Reproducibility

Training used a fixed seed (42) and the exact Phase 2 processed split (verified by dataset
hash match in `experiment.json` against `data/manifests/civil_comments_manifest.json`). The
run was not repeated end-to-end a second time on Colab (unlike Phase 3's two-run
verification) — GPU training reproducibility (cuDNN nondeterminism, etc.) was not separately
verified in this phase and is a documented limitation, not a claim.

## Critical decision: does DeBERTa justify its added complexity over TF-IDF + Logistic Regression?

**Yes, moderately-to-strongly, on model quality — but with real deployment costs that are
not yet fully quantified.**

The quality improvement is large and consistent across every primary metric (F1 +79%,
PR-AUC +80%, recall doubled), not a marginal or cherry-picked win. For a moderation system
where missed violations (false negatives) carry real cost, cutting the false-negative rate
from 77% to 54% is a meaningful, production-relevant improvement, not just a benchmark
number.

Against that: DeBERTa requires GPU training (M2 training was measured infeasible — a real,
not hypothetical, constraint), is 142M parameters to version/serve versus a few-KB linear
model, and its measured inference latency (~15.6ms p50 on a T4 GPU) has not been benchmarked
against the TF-IDF baseline on equivalent hardware, so the actual serving-cost tradeoff is
still an open question rather than a settled one. The threshold-selection instability (§
sweep caveat above) also means the 0.9 operating point should be treated as provisional, not
final, until re-validated on more data.

**Recommendation:** proceed with DeBERTa as a serving candidate, but do not treat this as
"production-ready" — the serving-cost and threshold-stability gaps above should be closed
(larger validation set, apples-to-apples latency comparison) before a real deployment
decision.

## Limitations

- Same 8,000-row prototype slice as Phase 3.
- Single-label (`toxicity` only).
- Decision threshold (0.9) selected on a validation set with only 61 positive examples —
  the sweep is noisy (see caveat above).
- Inference latency measured on Colab T4 GPU, not the M2 dev machine — not directly
  comparable to the baseline's M2 CPU latency numbers.
- Training was not repeated for a second reproducibility run in this phase (unlike Phase 3).
- Trained model weights were not retrieved from Colab at the time of writing; only the
  benchmark report and plots were downloaded (`models/text/deberta/v1/` is currently empty
  locally).
